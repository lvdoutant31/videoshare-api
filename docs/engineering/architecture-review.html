01 · 框架基础设施集中

Strongin-process
yingliu-common/.../common/web/{GlobalExceptionHandler,TraceIdFilter}.java
yingliu-service/.../service/persistence/{MybatisMapperConfiguration,MybatisPlusConfiguration,AuditMetaObjectHandler}.java
→ yingliu-framework/src/main/java/com/yingliu/framework/

Before · 运行规则散落

common
公共契约 + Servlet + 异常映射
service
业务规则 + Mapper 扫描 + 分页装配
理解一次请求处理，需要跨两个职责不同的 Module。

After · 一个技术装配位置

yingliu-frameworkWeb 异常映射 · Trace ID
Mapper 扫描 · 分页 · 审计时间
Spring / MyBatis 扩展点
↓ 依赖公共契约
yingliu-common

Problem技术规则跨 common 与业务 Module 分散，维护者难以定位装配位置。

Solution复用已有扩展 Interface，把技术 Implementation 集中到 framework。

  • Locality：装配集中
  • Leverage：请求共同受益
  • 测试覆盖同一 Interface
保留 Trace ID 和异常响应契约；common 的 BusinessException 仍使用 HttpStatus，需要轻量 spring-web。framework 不反向依赖业务 Module。

02 · 独立启动与配置归属

Strongin-process
yingliu-api-app/.../com/yingliu/YingliuApplication.java
yingliu-api-app/src/main/resources/ · 引用主类的整应用测试
→ yingliu-admin/ · 根 pom.xml · 部署构建入口

Before · App 入口兼任聚合器

yingliu-api-app
App 请求 + 启动 + 配置 + 数据库脚本
↓
api-admin
worker / media
管理端被 App Module 聚合，部署职责与请求职责交织。

After · 启动装配独立

yingliu-admin唯一启动入口 · 配置 · 脚本 · 集成测试
↓ 装配
api-app
api-admin
framework

Problem启动 Interface 隐藏在 App 请求 Module 内，跨端改动与运行配置耦合。

Solution独立后端工程以 yingliu-admin 装配各 Module，两个请求入口对等。

  • Locality：配置唯一归属
  • Leverage：一个部署入口
  • 整应用测试归属明确
主类保持 com.yingliu.YingliuApplication；既有 App 和管理端路径共同运行。迁移 Flyway 只改变文件位置，保留文件名、版本号和内容。

03 · 媒体配置与存储职责分离

Strongports & adapters
yingliu-media/.../media/storage/ 内的控制器、配置属性、存储实现
→ com.yingliu.media.controller · config · storage

Before · storage 收纳多种职责

storage
上传 / 签名 / 回调请求
配置读取 / Bean 装配
本地与 OSS 存储

After · 保留实际存储 Seam

controller · HTTP 适配
↓
storage · MediaStorage Interface
本地 Adapter　|　OSS Adapter
config · 属性与装配

Problem配置、请求入口和存储 Implementation 挤在一个包，变更位置缺乏 Locality。

Solution按职责分包，保留两个已有 Adapter 和 MediaStorage Seam，集中配置读取。

  • Locality：配置集中
  • Depth：隐藏存储差异
  • Leverage：复用已有 Interface
包迁移保留上传路径、存储 key、签名与回调语义；不通过重构引入新的存储协议。
