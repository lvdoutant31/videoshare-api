# 映流短视频系统技术选型说明

| 项目 | 内容 |
| --- | --- |
| 文档版本 | V1.0 |
| 上游文档 | 《短视频管理与播放系统 PRD》V1.1、《映流产品原型设计说明》 |
| 约束前提 | 小团队（2–5 人）、单机或少量内网服务器、本地媒体存储、企微集成、首期 H5 + PC 后台 |

## 1. 选型原则

1. **单体优先**：按 PRD 的六个系统边界做模块化单体，媒体转码与统计任务异步解耦，但不拆微服务。
2. **组件最少化**：单机部署下每引入一个中间件都是运维负担；能用 MySQL + Redis 解决的不再加新组件。
3. **国内生态成熟度优先**：企微 SDK、微信 JS-SDK、管理后台组件库均选国内资料最全的方案。
4. **为原生 App 保留能力**：API 与鉴权设计不绑定 Web，接口版本化。

## 2. 总体架构

```
                    ┌────────────────────────────────────┐
                    │            Nginx（网关）            │
                    │  HTTPS 终止 / 静态资源 / 媒体分发    │
                    └───────┬──────────────┬─────────────┘
                            │              │ X-Accel-Redirect
              ┌─────────────┴───┐    ┌─────┴──────────────┐
              │ Spring Boot 单体 │    │  本地媒体目录        │
              │  ├ api-app 手机端│    │  /media/original    │
              │  ├ api-admin 后台│    │  /media/transcoded  │
              │  ├ media 上传/凭证│   │  /media/cover       │
              │  ├ wecom 企微适配│    │  /media/tmp（分片）  │
              │  └ worker 异步任务│   └────────────────────┘
              └──────┬───────┬──┘
                     │       │
              ┌──────┴──┐ ┌──┴──────┐      ┌──────────────┐
              │ MySQL 8 │ │ Redis 7 │      │ FFmpeg（本地） │
              │ 业务+事件│ │缓存+队列 │      │ 转码/截帧     │
              └─────────┘ └─────────┘      └──────────────┘
```

单体内按 Maven 多模块划分：`yingliu-api-app`、`yingliu-api-admin`、`yingliu-media`、`yingliu-wecom`、`yingliu-worker`、`yingliu-common`、`yingliu-domain`。手机端与后台使用不同鉴权入口（两套 Token 域），共享 domain 层。

## 3. 后端技术选型

| 关注点 | 选型 | 理由与替代方案 |
| --- | --- | --- |
| 语言/框架 | Java 17 + Spring Boot 3.3.x | LTS 版本；生态成熟。不选 Spring Cloud——单体不需要 |
| ORM | MyBatis-Plus 3.5.x | 后台大量条件检索/分页表格场景效率高；逻辑删除、乐观锁开箱即用（PRD 要求逻辑删除） |
| 数据库 | MySQL 8.0（InnoDB, utf8mb4） | 唯一约束支撑点赞/收藏/关注/企微绑定的幂等关系模型；事件表按月分表预留 |
| 缓存 | Redis 7 + Redisson | 计数缓存、会话/播放凭证、限流（Redisson RRateLimiter）、分布式锁（审核任务领取锁定） |
| 任务队列 | Redis Stream（Redisson）+ 消费者组 | 承载转码、封面、定时发布、计数聚合、通知；支持 ACK/重试/死信记录，满足"至少一次+幂等"。单机下不引入 RabbitMQ/Kafka；若后续多机扩容再平滑替换为 RabbitMQ |
| 定时任务 | Spring Scheduling + ShedLock | 定时发布扫描、计数对账、备份校验；ShedLock 防多实例重复执行，为扩容预留 |
| 鉴权 | Sa-Token | 轻量、支持多账号体系（app/admin 双域）、注解式权限校验对齐 RBAC 到接口级；比 Spring Security 配置成本低得多 |
| 企微集成 | WxJava（weixin-java-cp） | OAuth 授权、扫码登录、JS-SDK 签名、成员查询均有封装；国内维护最活跃 |
| 分片上传 | 自研（本地文件系统） | 分片写 `/media/tmp/{uploadId}/`，Redis 记录分片位图，合并后 SHA-256 校验 + 原子 rename 入正式目录。不引入 MinIO——PRD 明确本地目录为主存储 |
| 转码 | FFmpeg + Java ProcessBuilder（worker 内串行/小并发池） | 输出 H.264 MP4（faststart，720p/480p 两档）+ 截帧封面；隔离在 worker 进程组，失败清理临时文件 |
| 媒体分发 | Nginx `X-Accel-Redirect` 内部重定向 | 业务接口校验短期播放凭证（Redis，含视频状态检查）后交给 Nginx 做 Range/断点续传；应用不承担文件 IO，客户端不可见真实路径，天然防目录穿越 |
| 敏感词 | ToolGood.Words（Java 版）或 Aho-Corasick 自建 | 内存词库 + 后台配置热更新 |
| API 文档 | SpringDoc OpenAPI (Swagger UI) | 契约测试与前端联调基础 |
| 参数校验 | Jakarta Validation | 统一错误码封装：`{code, message, traceId}` 对齐 PRD 错误契约 |
| 日志/审计 | Logback JSON + traceId（MDC）；审计日志独立表 | 审计表仅 insert，无 update/delete 权限 |

### 关键设计决策

- **播放凭证**：`GET /api/v1/videos/{id}/play-token` 签发 5 分钟 Redis 凭证 → `GET /media/play/{token}` 校验后 `X-Accel-Redirect` 到内部 location。下架视频在签发环节即被拒绝，满足"下架后旧链接失效"。
- **互动幂等**：点赞/收藏/关注接口按目标状态设计（`PUT .../like { liked: true }`），DB 唯一键 `(user_id, target_id)` 兜底，Redis 计数 + 每日对账任务校准。
- **计数**：关系表为事实来源，`video_stats` 聚合表快速展示，worker 异步增量更新 + 定时全量校准。
- **事件埋点**：客户端批量上报 → 事件原始表（按月分表）→ worker 日级聚合到指标表。首期不引入 ClickHouse，日活预期内 MySQL 足够；预留事件表结构对齐后续迁移。

## 4. 前端技术选型

两个独立前端工程，共享一个 `packages/shared`（API client、类型、常量），用 pnpm workspace 管理。

### 手机端 H5（`yingliu-c`）

| 关注点 | 选型 | 理由 |
| --- | --- | --- |
| 框架 | Vue 3.4+ + TypeScript + Vite 5 | 组合式 API；Vite 开发体验 |
| 状态 | Pinia | 用户会话、播放器全局状态（静音记忆、当前播放实例） |
| 路由 | Vue Router 4 | 登录返回原视频依赖路由守卫 + redirect 参数 |
| UI 组件 | Vant 4 | 底部抽屉（评论面板）、ActionSheet（分享面板）、Toast、上传等移动端组件齐全；暗色主题定制对齐"暗场影像"视觉 |
| 视频流 | 自研全屏滑动容器 + 原生 `<video>` | swiper 类库对"单实例播放+快速滑动只播最终项"控制不够精细；自研虚拟三屏（prev/current/next）结构，IntersectionObserver 控制播放 |
| 播放器 | 原生 `<video>`（MP4 Range） | 转码产物为渐进式 MP4，无需 HLS；不引入 video.js/xgplayer，减小包体、避免全屏手势冲突。首帧优化靠 `preload="metadata"` + 预加载下一条 |
| 微信/企微分享 | weixin-js-sdk + 企微 agentConfig | 环境探测（UA 判断微信/企微/普通浏览器）决定分享面板降级路径 |
| 请求 | Axios + 拦截器 | 统一错误码、traceId 透传、401 跳登录 |
| CSS | UnoCSS + CSS 变量 | 品牌色 token（墨黑/流光青/珊瑚）以 CSS 变量落地，对齐原型 Foundations |
| 埋点 | 自研轻量 SDK | 批量队列 + `sendBeacon` 兜底（页面隐藏时） |

### PC 后台（`yingliu-b`）

| 关注点 | 选型 | 理由 |
| --- | --- | --- |
| 框架 | Vue 3 + TypeScript + Vite（同 H5） | 技术栈统一，小团队维护成本最低 |
| UI 组件 | Element Plus | 高密度表格、树形权限、表单校验最成熟；浅色主题对齐"明场运营" |
| 图表 | ECharts 5 | 工作台趋势图 |
| 上传 | 自研分片上传组件 | spark-md5 分片哈希 + 并发 3 分片 + 断点续传（查询已传分片位图）|
| 视频预览 | 原生 `<video>` | 审核页预览 |
| 权限 | 路由守卫 + 指令 `v-perm` | 前端隐藏 + 后端 Sa-Token 注解双重校验 |

## 5. 基础设施与部署

| 项 | 选型 |
| --- | --- |
| 部署 | Docker Compose 单机编排：nginx / app（业务+worker 同 JVM，可配置拆分）/ mysql / redis |
| 媒体磁盘 | 独立数据盘挂载 `/media`；备份盘独立物理磁盘 |
| 备份 | mysqldump 每日全量 + binlog；媒体目录 rsync 每日增量到备份盘/备份机（cron）|
| 磁盘告警 | worker 定时采集磁盘使用率 → 80% 预警 / 90% 告警并置"暂停上传"全局开关（Redis）|
| HTTPS | Nginx + 证书（企微回调要求 HTTPS）|
| CI | 有 GitLab 用 GitLab CI，否则 GitHub Actions：构建 → 测试 → 镜像 → 手动部署脚本 |
| 监控 | 首期最小方案：Spring Boot Actuator + 日志告警脚本（企微机器人 webhook 通知转码积压/任务失败/磁盘告警）；Prometheus+Grafana 列为 V1.1 |

## 6. 测试技术栈

对齐 PRD Testing Decisions 的两条基线：

| 层 | 工具 |
| --- | --- |
| 单元测试 | JUnit 5 + AssertJ（状态机、排序规则、计数规则、权限决策表驱动） |
| 集成测试 | Testcontainers（MySQL/Redis 真实容器）；文件系统用 JUnit `@TempDir`；企微/FFmpeg 用可控接口替身 |
| API 契约测试 | Spring MockMvc/RestAssured + OpenAPI 校验（基线一） |
| 手机端 E2E | Playwright（移动视口 + 网络节流模拟弱网；自动播放/滑动切换/失败恢复）（基线二） |
| 前端单测 | Vitest + Vue Test Utils |
| 性能测试 | k6（流接口、并发 Range 读取、互动写入） |

## 7. 明确不选的方案

| 不选 | 原因 |
| --- | --- |
| 微服务 / Spring Cloud / K8s | 小团队单机，PRD 明确模块化单体即可 |
| MinIO / 云 OSS | PRD 明确本地目录为主存储 |
| RabbitMQ / Kafka | Redis Stream 满足首期吞吐与重试语义，少一个运维组件；扩容时再评估 |
| HLS / DASH 流媒体协议 | 10 分钟内短视频，渐进式 MP4 + Range 足够，首帧更快、链路更简单 |
| Elasticsearch | V1 无关键词搜索；V1.1 搜索先用 MySQL 全文索引评估 |
| ClickHouse | 事件量在 MySQL 分表承受范围内 |
| uni-app / Taro 跨端 | 首期只有 H5，纯 Vue Web 更轻；原生 App 阶段再评估 |
| 完整 IM 组件 | 站内转发只是不可回复卡片，普通业务表即可 |

## 9. 待评审确认项

1. 转码清晰度档位（建议 720p 主档 + 480p 弱网档）与码率参数。
2. 业务与 worker 是否首期同 JVM 部署（建议同 JVM、以线程池隔离，转码进程数上限 2）。
3. 企微机器人告警 webhook 是否可用（决定监控最小方案落地方式）。
4. 服务器规格与媒体盘容量（决定磁盘阈值绝对值与备份策略细节）。
